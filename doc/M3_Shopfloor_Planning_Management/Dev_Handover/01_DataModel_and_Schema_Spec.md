# M3 · 01 — Data Model & Schema Spec
**Pairs with:** `M3_schema.sql` (runnable PostgreSQL 15+). **Deep-plan ref:** §11 (data contract), §5 (postures), §12 (boundaries).

## 1. Where M3 sits in the canonical model
M3 owns the `ops` schema and **FKs into `canon.*`**; it never alters canon core. It **brings to life** four canonical entities that were catalogued (doc 01 §10–11) but not yet built (no prior module needed them): `Material`, `BOM`, `ProductionOrder`, `ProductionOperation`. It **introduces** (additive, doc 01 §14): `Routing`/`RoutingOperation`, `WorkCenterCapacity`, `SetupMatrix`, `DemandForecast`, `MPSLine`, `PlannedOrder`, `ScheduleEntry`, `ProductionConfirmation`, `ShiftHandover`/`HandoverCarryover`, `MaterialStock`, `MrpRun`, `kpi_plan_daily`.

## 2. Conventions (inherited from `02_CanonicalDataModel_Spec §5`)
`lower_snake_case` · surrogate `BIGINT GENERATED BY DEFAULT AS IDENTITY` · `UUID tenant_id` on every row · `TIMESTAMPTZ` UTC · units embedded in column names · `ext JSONB` extension namespace · `source_ref` provenance on ingested rows · FK to `canon.*` masters (no free-text coded values).

## 3. The soft-reference rule (canon independence)
`canon.event.order_ref` is a plain `BIGINT` (doc 02 §5 DDL — no hard FK). M3 places `ops.production_order.order_id` into it. **No cross-schema hard FK from canon→ops**, so the canonical core stays independent of M3 — the same rule M2 uses for downtime classification. Likewise `ops.production_confirmation.canon_event_ref` softly points at the `canon.event` ProductionCount row M3 books.

## 5. Posture-driven population (same model, three doors)
The `enum order_source` (`ERP_IMPORT | MRP_GENERATED | MANUAL | M1_PLAN_CSV`) records *who authored* each `demand_forecast`/`mps_line`/`planned_order`/`production_order` row. In **Posture A/B** these are `ERP_IMPORT` (or `M1_PLAN_CSV`); in **Posture C** the MRP engine writes `MRP_GENERATED`. Downstream scheduling/execution/KPI code reads the same columns regardless — so posture is data, not a code fork (deep-plan §5).

## 6. Acceptance criteria
- **MUST** create `ops` schema and all tables with `tenant_id` + `ext JSONB` on every row.
- **MUST** keep canon independent: no FK from `canon.*` to `ops.*`; `order_ref`/`canon_event_ref` are soft.
- **MUST** FK every coded reference to a master (`material_ref`, `work_center_ref`→`canon.equipment_node`, `shift_ref`→`canon.shift`, `*_ref`→`canon.personnel`).
- **MUST** record one ProductionCount per produced quantity (no double-book vs M4).
- **MUST** support all three postures without schema change (validated by populating each `order_source`).
- **SHOULD** pass M1 `coil_plan`/`prod_*` through conformance into `production_order`/`production_confirmation` with zero loss.
- **SHOULD** validate via `pglast.parse_sql` in CI (as M2 does).

## 7. Build phasing
**M3-0:** schema + masters + `planning_config`. **M3-1:** order lifecycle, confirmation, handover. **M3-2:** schedule_entry + setup_matrix + KPI mart. **M3-3:** demand/MPS/MRP + material_stock (Posture C). **M3-4:** optimiser tables stay as-is (no re-model).
