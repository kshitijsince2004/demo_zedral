# M1 (Data Capture Layer) — ZedralV2.1 → zedral_v4 Difference Report & Migration Guide

> **Audience:** coding agent / IDE. All paths are repo-relative.
> **Repo A (source):** `ZedralV2.1-main` — monolith, M1 is the entire app.
> **Repo B (target):** `zedral_v4-main` — modular monolith, M1 is one registered module among M1–M4.
> **Scope:** M1 ONLY. Ignore `maint/*` (M2), `plan/*` + `m3/*` (M3), `oee/*` + `m4/*` (M4).

---

## 1. What M1 is

M1 = "Data Capture Layer" (v4 manifest name: **"Digital Data Collection"**, module code `M1`).
It digitizes 11 paper log sheets across 8 process lines of a cold-rolling steel plant:
`HRS (HR Slitting) → PKL (Pickling) → CRM 2HI/4HI/6HI (Cold Rolling) → ANN (Annealing) → SKP (Skin Pass) → RWD (Rewinding) → CRS (Circle/Slitting) → CTL (Cut-to-Length)`.
`COIL_NO` is the traceability spine; every process appends to the same coil record.

## 2. High-level M1 delta (V2.1 → v4)

| # | Area | V2.1 | v4 |
|---|---|---|---|
| 1 | Packaging | M1 is the whole app; no module concept | M1 is a registered module `@zedral/m1-collection` with a manifest |
| 2 | Route gating | All routes always on | Every M1 route wrapped in `m1Guard` (per-tenant feature flag `module.m1_collection`) |
| 3 | Events | In-process `EventEmitter` only (`DomainEventPublisher`) | Platform EventBus; M1 publishes `shift.closed`, `downtime.logged`, `production.counted` |
| 4 | Canonical data | None | M1 writes `canon.production_count` and `canon.event` (downtime) via `/v1/canon` write-back API |
| 5 | Per-process capture (HRS/PKL/ANN/SKP/RWD/CRS/CTL) | NOT implemented — non-CRM machines route to a "Coming Soon" page | Implemented: `/production` REST endpoints + `ProductionService` + client capture forms (prototype quality) |

| 7 | Reporting/Live services | Single files | Split into `services/reporting/` and `services/live/` |

| 9 | Client shell | `PlantHeadShell` | `UnifiedShell` + `UnifiedHeader` + `Breadcrumbs` (all-module shell) |

| 12 | Validation schemas | Field registry only | + `shared-validation/src/rules/m1Forms.ts` (Zod schemas for the 7 process forms) |

## 3. Detailed differences

### 3.1 M1 module packaging (NEW in v4)

**New package: `packages/modules/m1-collection/`** (npm name `@zedral/m1-collection`)

```
packages/modules/m1-collection/
├── package.json
├── tsconfig.json
└── src/
    ├── index.ts          # re-exports manifestMeta
    └── manifestMeta.ts   # the M1 manifest metadata
```

`manifestMeta.ts` (exact contents that must exist):

```ts
export const M1_MODULE_CODE = 'M1' as const;

export const m1ManifestMeta = {
  code: M1_MODULE_CODE,
  name: 'Digital Data Collection',
  dbSchema: 'txn',
  featureFlag: 'module.m1_collection',
  mountPath: '/',
  consumesEvents: [] as const,
  producesEvents: [
    'shift.closed',
    'downtime.logged',
    'production.counted',
    'defect.logged',
  ] as const,
  consumesCanonical: [] as const,
  dependsOn: [] as const,
  migrationsPath: 'migrations/modules/m1',
};
```

**New server-side module dir: `packages/server/src/modules/m1-collection/`**

```
packages/server/src/modules/m1-collection/
├── register.ts                      # createM1Manifest() + registerM1Module(registry)
├── routes/productionRoutes.ts       # NEW per-process capture endpoints
└── services/ProductionService.ts    # NEW per-process persistence + event emission
```

`register.ts` builds a `ModuleManifest` from `m1ManifestMeta` with `createRouter: () => Router()` (empty — M1 legacy routes are mounted individually in `app.ts`, the manifest exists for registry/CI ownership tracking) and `getSchedulers: () => []`.

**Schema ownership (per `doc/m1/D12_Schema_Ownership_Map.md`):** M1 owns Postgres schemas `txn` (shift_log, stoppage_entry, production, defects, 6HI orders), `planning` (import_batch, ppc_batch, planned_coil), `coil` (coil, coil_process_history), `master` (shift, machine, grade, stoppage_code, customer — shared reference data, read-only for other modules). Rule: no other module's migration may CREATE/ALTER objects in these schemas; cross-module flow is canonical read / events / write-back only.

### 3.2 Platform kernel dependency (NEW in v4)

M1 in v4 depends on `packages/platform/` (`@zedral/platform`), which exports:

- `ModuleRegistry`, `ModuleManifest` (`registry/`)
- `requireModule(moduleCode, featureFlag, loadConfig)` middleware — returns **404** `"Module Not Enabled"` when the tenant flag is off (per D12a B6)
- `EventBus` abstraction with `InProcessEventBus`, `RedisEventBus`, `KafkaEventBus` implementations; `getEventBus()`, `initEventBus()`, `shutdownEventBus()`, `buildEventEnvelope()` (`eventbus/`)
- `canonicalWriteback` / `WritebackClient` (`writeback/`)
- canonical entities + event contracts (`canonical/`)
- `validateServiceToken` (`security/serviceAuth.ts`)
- `resolveActiveModules`, `isModuleActive` (`tenant/moduleResolver.ts`)

### 3.3 App bootstrap & route gating

**V2.1:** `packages/server/src/index.ts` creates the express app inline and mounts every route ungated.

**v4:** split into:
- `packages/server/src/app.ts` — composition root, `buildApp(registry): ComposedApp`. Creates `m1Guard = requireModule('M1', m1ManifestMeta.featureFlag, getTenantModuleConfig)` and mounts **all** M1 routes behind it:

```
/device /planned-coils /6hi /live /machines /machine-access /machines/handover
/shifts /shift-logs /stoppages /crew /defects /import /master-data /users
/reports /exports /traceability /validation-rules /audit /production
```

  (`/auth` stays ungated; `/v1/canon` uses service-token auth instead of the guard.)
- `packages/server/src/index.ts` — slim entrypoint: `initEventBus()` → `buildModuleRegistry()` → `buildApp(registry)` → `startModuleRuntime()`; also defaults `CANONICAL_WRITEBACK_URL` to `http://127.0.0.1:${port}/v1/canon`.
- New middleware chain: `contextMiddleware` → `tenantScopeMiddleware` (new file `middleware/tenantScopeMiddleware.ts`); RFC-7807 error handler (`middleware/errorMiddleware.ts` / `utils/errorHandler.ts`).
- New supporting files: `src/platform/tenantConfig.ts` (loads `security.tenant_config` → `TenantModuleConfig`), `src/modules/registerModules.ts`, `src/modules/moduleRuntime.ts`, `src/db/withTenant.ts`.

### 3.4 Event emission + canonical write-back (NEW in v4 — the key M1 behavioral change)

**New file: `packages/server/src/platform/m1Events.ts`.** Exports:

- `publishShiftClosed({ shiftLogId, processId, totalProdMt, closedAt? })`
  → publishes envelope `shift.closed` v1, key `` `${tid}:shift.closed:${shiftLogId}` ``, lineage `shift_log:<id>`; if `totalProdMt > 0` it also calls `publishProductionCounted`.
- `publishProductionCounted({ shiftLogId?, assetId, quantity, uom?='MT', countedAt? })`
  → FIRST writes a row via `canonicalWriteback.createProductionCount(tid, {...})` (→ `canon.production_count`), THEN publishes `production.counted` v1 keyed by the returned `count_id`.
- `publishDowntimeLogged({ stoppageId, shiftLogId, stoppageCode, fromTime, toTime, durationMin, prodDate })`
  → writes `canonicalWriteback.createDowntimeEvent` (→ `canon.event`, `event_type: 'downtime'`, lineage `stoppage:<id>`), resolves downtime `category` (`MECH|ELECT|UTILITY`) from `master.stoppage_code.category` with code-prefix fallback, then publishes `downtime.logged` v1.
- `resolveAssetIdForShiftLog(shiftLogId)` — maps process code → canonical asset id via `PROCESS_ASSET_MAP = { '6HI':'101', '4HI':'102', '2HI':'103', CRM:'101' }`, falling back to first `canon.equipment_node`.

**Hook points (small diffs in existing files):**
- `services/shiftLogService.ts` — after shift close: `void publishShiftClosed({...}).catch(...)` (fire-and-forget, logs `[M1] failed to publish shift.closed`).
- `services/StoppageService.ts` — after stoppage insert: `void publishDowntimeLogged({...}).catch(...)`.

**Note:** `defect.logged` is declared in the manifest `producesEvents` but is **not yet emitted anywhere** in v4 code (known gap).

**Canonical write-back corridor (NEW):**
- `packages/server/src/routes/canonRoutes.ts` mounted at `/v1/canon` — auth via `validateServiceToken(Authorization)` (service token, NOT user JWT) + required `x-tenant-id` header; delegates to `src/platform/canonApiService.ts`.
- `src/platform/canonicalRead.ts`, `src/platform/eventPublisher.ts` also new.
- `DomainEventPublisher.ts` was rewritten: V2.1 = `class DomainEventPublisher extends EventEmitter`; v4 = typed event interfaces published through `getEventBus()` from `@zedral/platform`.

### 3.5 Per-process production capture (NEW FEATURE in v4)

**V2.1 state:** `txn.prod_hrs`, `prod_hrs_slit`, `prod_pkl`, `prod_ann`, `prod_skp`, `prod_rwd`, `prod_crs`, `prod_ctl` tables already exist in the baseline migrations and are read by export/traceability/shift-log paths, but there is **no dedicated capture API and no operator UI** — client routes any non-CRM machine to `/coming-soon/:machineCode` (`pages/MachineComingSoon.tsx`; `lib/machineRouting.ts` returns `` `/coming-soon/${machineCode}` ``, and operator nav lists CRM mills only).

**v4 additions:**

Server (`src/modules/m1-collection/`):
- `routes/productionRoutes.ts` — `POST /production/hrs|pkl|ann|skp|rwd|crs|ctl`; Zod `validateBody(schema)` per route; `injectContext` middleware backfills `tenantId` from `requestContext`. PKL accepts `{ ...data, charts: PKLChartRow[] }`.
- `services/ProductionService.ts` — static `saveHrs/savePkl/saveAnn/saveSkp/saveRwd/saveCrs/saveCtl`, each a Kysely transaction inserting into `txn.prod_*` (+ child tables `txn.prod_hrs_slit`, CRS slit slots, SKP passes, PKL hourly chart rows), then `emitCaptured()` → EventBus event `production.captured` v1.

Shared validation:
- **New file** `packages/shared-validation/src/rules/m1Forms.ts` — `baseProcessEntrySchema` (id/tenantId/machineCode/shiftLogId/coilNo/createdAt/createdBy) + `hrsSchema`, `pklSchema`, `annSchema`, `skpSchema`, `rwdSchema`, `crsSchema`, `ctlSchema`, `hrsSlitSlotSchema` (labels A–D), `crsSlitSlotSchema`, `skpPassSchema` (passNo 1–6). Exported types `HRSEntry`, `PKLEntry`, `PKLChartRow`, etc.
- `packages/shared-validation/src/index.ts` adds `export * from './rules/m1Forms';`.
- Route schemas import from alias `@m1/shared-validation`.

Client:
- **New** `pages/capture/GenericCapturePage.tsx` — route `/capture/:machineCode`; switch on code → `HrsCaptureForm | PklCaptureForm | AnnCaptureForm | RwdCaptureForm | CrsCaptureForm | CtlCaptureForm`, default → `MachineComingSoon`.
- **New** `pages/capture/ProcessForms.tsx` — the 7 form components (`SkpCaptureForm` exists but is **not wired** into the switch).
- `lib/machineRouting.ts` changed: `pathForMachine` → `` `/capture/${machineCode}` ``; operator nav lists ALL accessible machines (CRM mills first, then others) instead of CRM-only.
- `App.tsx` adds `<Route path="/capture/:machineCode" element={<ProtectedRoute><GenericCapturePage /></ProtectedRoute>} />`.

**⚠ Known defects in the v4 capture layer (prototype quality — fix during/after migration):**
1. `ProcessForms.tsx` posts to `` `/api/v1/m1/production/${endpoint}` `` but the server mounts at `/production` — path mismatch unless the reverse proxy rewrites it.
2. Hidden form fields inject mock values: `machineCode = MOCK-<TYPE>`, `shiftLogId = SL-<Date.now()>`, `coilNo = COIL-<Date.now()>` — must be replaced with real shift/machine context from `authStore`/active shift log.
3. User feedback via `alert()`; no toast/optimistic UI; forms don't use the offline `syncQueue`.
4. `productionRoutes.ts`, `ProductionService.ts` carry `// @ts-nocheck`.
5. `/production/pkl` bypasses `validateBody` and parses inline; charts skip strict validation.
6. `defect.logged` declared but never published.
